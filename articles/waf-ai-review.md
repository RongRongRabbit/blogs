## はじめに

設定ファイルを AI に渡して、「この設定で問題ないですか？」と聞くことがあります。

説明を読んで、自分でも確認する。気になるところがあれば、もう少し詳しく聞く。私も、そういう使い方をしています。

ただ、設定のレビューを任せるなら、何を確認できれば「正しく読めている」といえるのでしょうか。

きっかけは、[AWS Security Blog の Steering File に関する記事](https://aws.amazon.com/blogs/security/configuring-your-ai-vulnerability-harness-part-2-the-steering-file/)でした。AI に確認方法を明示するという考え方を参考に、今回は WAF の関連付けに絞った小さな設定レビューを試しました。

同じモデルに同じ資料を渡し、通常のレビュー指示と、確認手順を追加した指示を比較しています。元記事の脆弱性検証を再現したものではなく、独自に用意した合成ケースでの実験です。

最初は、手順を詳しく書けば読み落としが減るのではないか、と考えていました。ところが、結果はその予想どおりにはなりませんでした。

## WAF のルールは、本番環境に適用されているか？

AWS WAF は、Web アプリケーションへの HTTP／HTTPS リクエストを検査し、ルールに応じて許可・ブロックするサービスです。ルールは Web ACL にまとめ、API Gateway などの保護対象に関連付けます。

そのため、設定を確認するときは、**ルールの内容と、その適用先の両方**を見る必要があります。

今回は、API Gateway に開発用の `dev` と本番用の `prod` がある設定を用意しました。この公開先の単位を Stage と呼びます。

確認するのは、**本番の `prod` に送ったリクエストを、この WAF 設定で止められるか**です。

| ケース | 確認対象 | WAF の関連付け先 |
|---|---|---|
| Q2 | `prod` | `prod` |
| Q4 | `prod` | `dev` |

両ケースのルールは同じで、リクエストのヘッダー `x-lab-mode` が `maintenance` と完全一致したら、`Block`（ブロック）します。それ以外のリクエストは通す設定です。

Q2 は対象の本番環境に適用されます。一方、Q4 にも同じ Block ルールはありますが、適用先が開発環境なので、本番のリクエストをこの WAF では止められません。

Q4 の設定を見ると、確認対象は `prod`、WAF の関連付け先は `dev` になっています。

![Q4の確認対象とWAFの関連付け先](/images/waf-ai-review/01-stage-comparison.png)

AWS WAF の関連付け先を指定する `ResourceArn` には、API Gateway の Stage 名も含まれます。詳しくは、[AssociateWebACL の公式ドキュメント](https://docs.aws.amazon.com/waf/latest/APIReference/API_AssociateWebACL.html)で確認できます。

:::message
今回は合成の設定ファイルを使っています。AWS にリソースをデプロイしたり、実際のリクエストが止まることを確認したりした実験ではありません。「止める／止めない」は、提示した設定からの静的な判定です。
:::

## AI に何を渡したか

確認対象と WAF 設定を、別々のファイルに置きました。

| ファイル | 内容 |
|---|---|
| `scope.json` | 確認対象の Stage と、リクエストの情報 |
| `infra.json` | WAF のルールと関連付け |
| `src/app.py` | ヘッダーの値を返す小さな処理例 |

AI には、この3つをファイル名と行番号付きで渡します。正解を保存したファイルは渡しません。

`scope.json` では、提示した資料がこの合成ケースの WAF 設定の全範囲であることも定義しています。資料にない別の WAF を想定せず、この範囲で判断するためです。

このくらいの設定なら、人が読んでも、プログラムで比較しても判断できます。今回は、複数の資料を読んで設定レビューをする AI が、どんな回答を返すかを確かめるために使っています。ケースを小さくしたのは、回答を自分で確認できるようにするためです。

また、「リクエストを止めるか」だけでなく、設定をどう読んだかも回答してもらいます。

例えば Q4 なら、次のようになります。

| 確認すること | 正しい答え |
|---|---|
| WAF が対象の `prod` に関連付けられているか | いいえ |
| 提示したルールの条件にリクエストが一致するか | はい |
| 提示したルールの検査位置 | ヘッダー |
| 提示したルールの動作 | Block |
| この設定で対象のリクエストを止めるか | いいえ |

ここでは、**「本番に適用されていない」と「ルールが存在しない」を分けて回答してもらう**ことにしました。

## 確認手順も渡してみる

比較したのは、次の2グループです。

- **A：確認項目の意味と回答形式を指定して、レビューを依頼する。**
- **B：A と同じ定義と回答形式に、確認手順を追加する。**

B の追加手順は Markdown ファイルに保存し、モデルへのリクエストに読み込ませています。このファイルを、今回の PoC では Steering File と呼んでいます。

### A：通常のレビュー指示

A/B 共通で、各項目の意味と JSON の回答形式を指定しています。そのうえで、A には次のレビュー指示を渡しました。

```text
提供されたリクエストと WAF 設定を確認し、指定された事実と根拠の位置を回答してください。
```

A も、何も定義せずに「確認してください」とだけ依頼したグループではありません。

### B：確認手順を追加した指示

B には、同じ共通指示に加えて、関連付け、条件、動作を順番に確認する手順を渡しました。

ARN は、AWS のリソースを識別する文字列です。今回は、その中に含まれる Stage が違えば、同じ対象への関連付けではありません。

まず2つの ARN を比較し、次にルール条件を確認し、最後に対象を止める設定かを判断するよう求めています。

:::details B に追加した指示の全文

```text
次の3段階で設定を照合してください。

1. 対象への関連付け
scope.json の target_stage_arn と、infra.json の対象 WebACL を参照する Association の ResourceArn を全文比較してください。
完全に同じなら waf_associated=true、異なるか対象への関連付けがなければ false としてください。

2. ルールの条件
request_matches_rule は、リクエストの値がルールの検査位置と比較条件に一致するかで判断してください。
関連付けの有無とは別に判定してください。

3. 対象リクエストの扱い
この実験の単一ルール・既定 Allow の設定では、
waf_associated=true、request_matches_rule=true、action=Block の3条件がそろった場合だけ request_blocked_by_config=true としてください。
それ以外は false としてください。実環境での観測がなければ runtime_verified=false としてください。

evidence には比較した2つの ARN の行を含めてください。
関連付けがない場合は、それを確認した Resources の位置を示してください。
共同指示の JSON 形式を守り、explanation は日本語の短い1文にしてください。
```

:::

特定のケースの答えは書かず、資料の確認方法を指定しました。

なお、この3条件で判断できるのは、今回の単一ルール・既定 Allow の設定に限ります。複数のルールや Rule Group がある WAF 設定を、そのままこの式で判断できるわけではありません。

## 指示を固定して、各ケースを3回ずつ実行

同じモデルと生成パラメータで、A/B それぞれに Q2 と Q4 を3回ずつ渡しました。

**2グループ × 2ケース × 3回で、合計12回**です。

今回使用したモデルと生成パラメータは、以下のとおりです。
A/B 両グループに同じ設定を使用しました。

![検証時のモデルと生成パラメータ](/images/waf-ai-review/05a-run-settings.png)

モデルの呼び出しには、Amazon Bedrock の Converse API を使っています。実行条件は `manifest.json` に保存し、リクエストと回答も残します。

```bash
python3 run.py --groups A B --cases Q2 Q4 --repeats 3
python3 evaluate.py results-stage/実際の結果ディレクトリ
```

`run.py` はモデルを呼び出し、`evaluate.py` は保存済みの回答を設定と照合します。評価処理ではモデルを追加で呼び出しません。

評価では、最終判定だけでなく、次の6項目を確認しました。

| 項目 | 確認する内容 |
|---|---|
| `request_matches_rule` | 提示したルールとリクエストの条件が一致するか |
| `waf_associated` | WAF が確認対象の Stage に関連付けられているか |
| `inspection_field` | 提示したルールの検査位置 |
| `action` | 提示したルールの動作 |
| `request_blocked_by_config` | この設定で対象のリクエストを止めるか |
| `runtime_verified` | 実環境で動作を確認したか |

今回、実環境での動作確認はしていないので、`runtime_verified` の正しい値はすべて `false` です。

:::details 検証条件について

予備実験の結果をもとに、A/B 共通の項目定義と B の確認手順を修正しました。本記事では、修正後の指示を固定して実行した12回の結果を扱い、修正前の結果とは合算していません。

指示の調整と評価に同じケースを使っているため、未知の設定への効果は未検証です。

:::

## 「止めるか」は、すべて正解だった

12回とも、指定した JSON 形式で回答が返りました。内容フィルターによる停止もありませんでした。

まず、「この設定で対象のリクエストを止めるか」という判定だけを見ると、A/B ともすべて正解です。

ただ、回答した設定の事実まで確認すると、違いがありました。

| 評価項目 | A | B |
|---|---:|---:|
| 有効な回答 | 6/6 | 6/6 |
| 対象を止めるかの判定が正しい | 6/6 | 6/6 |
| 設定の6項目がすべて正しい | 6/6 | 4/6 |
| Q2 の6項目がすべて正しい | 3/3 | 3/3 |
| Q4 の6項目がすべて正しい | 3/3 | 1/3 |

B の2回答は、Q4 の設定を読み違えていました。

## 適用先が違うだけなのに、ルールがないことになっていた

B の Q4-1 と Q4-2 では、次の回答が返りました。

| 項目 | 設定から確認できる事実 | B の回答 |
|---|---|---|
| ルールの条件に一致するか | true | false |
| 対象の `prod` に関連付けられているか | false | false |
| ルールの検査位置 | SingleHeader | NONE |
| ルールの動作 | Block | NONE |
| 対象のリクエストを止めるか | false | false |
| 実環境で動作確認済みか | false | false |

関連付け先が `prod` ではないことと、本番のリクエストを止めないという判定は合っています。

でも、`infra.json` にはヘッダーを検査する Block ルールがあります。関連付け先が `dev` だからといって、その設定がなくなるわけではありません。

![Bの回答（Q4）](/images/waf-ai-review/03-q4-facts.png)

対象を止めないという判定は正しい一方、条件一致・検査位置・アクションは設定と食い違っています。

**対象に適用されないことは、設定にルールが存在しないことを意味しません。**

モデルが内部でどう判断したかは、出力だけではわかりません。ただ、最終判定が合っていても、設定の事実には誤りがあることは確認できます。

「止めるか」だけを採点していたら、この2回答も正解として扱っていたところでした。

## 設定と照合すると、間違いを見つけられた

設定レビューの結果を、原因調査や修正の検討にも使うなら、この違いは気になります。

「ルールはあるが、関連付け先が違う」と「ルールがない」では、次に確認する場所が変わるからです。

そこで PoC には、入力設定をプログラムで読み直す処理も用意しました。

`verify.py` が関連付け先、ルールの条件、検査位置、動作を確認し、モデルの回答と比較します。食い違いがあれば、`REVIEW_REQUIRED`、つまり「人の確認が必要」とします。

今回の2回答も、次の3項目の不一致で検出できました。

- ルールの条件に一致するか。
- ルールの検査位置。
- ルールの動作。

![照合処理が検出した不一致](/images/waf-ai-review/04-review-required.png)

この処理は、評価用の正解表を見て回答を書き換えるものではありません。入力の設定から事実を計算し、モデルの回答との違いを示します。

ただし、対応範囲は今回のサンプルに限定しています。任意の CloudFormation や複雑な WAF 設定を検証できるツールではありません。

また、根拠の行番号が存在することと、その行が判断を十分に支えることも別です。今回の自動照合で、自然言語の説明まで正しいと保証しているわけではありません。

## 確認手順を増やせばよい、とはいえなかった

今回、確認手順を追加した B が、A より正確になる結果は得られませんでした。

A は6回答すべての設定の事実が正しく、B は2回答に誤りがありました。一方で、対象を止めるかの最終判定は、両グループとも正解でした。

ここから「Steering を使うと精度が下がる」とまではいえません。ケースは2つだけで、指示の調整にも同じケースを使っています。別のモデルや設定で、同じ結果になるかも未確認です。

それでも、今回の回答を見て、レビュー結果の受け取り方は変えたいと思いました。

「この設定で止められますか？」という最後の答えだけでは、何を読んでそう判断したのかわかりません。

適用先、条件、動作も受け取り、設定と突き合わせる。プログラムで確かめられる部分は照合し、扱えない部分は人が確認する。今回のような事実の読み違いは、その形にして初めて見つけられます。

:::message
この記事で分析したのは、構造化された `facts` の誤りです。自然言語の `explanation` 全文の正しさや、修正案の品質、レビュー時間の削減効果は評価していません。
:::

## まとめ

今回は、AWS WAF の2つの合成設定を使い、通常のレビュー指示と、Steering File で確認手順を追加した指示を比較しました。

12回の回答すべてで、対象のリクエストを止めるかという最終判定は正解でした。一方、Steering File を追加したグループでは、2回の回答にルールの条件・検査位置・動作の読み違いがありました。

今回の範囲では、確認手順の追加による精度向上は確認できませんでした。ただ、最終判定だけでは見落とす誤りを、設定との照合によって見つけられました。

AI に設定レビューを依頼するときは、結論に加えて、判断に使った設定の事実と根拠も受け取り、確認できる形にしておくことが大切だと感じました。

この記事が、AI を使った設定レビューを試す際に、**何を任せて、どこを自分やプログラムで確認するか**を考える参考になれば幸いです。
